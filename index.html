01 About This Machine

What it is, and why the rules below matter.

This machine is an NVIDIA DGX Spark, a small desktop AI computer built around a single GB10 Grace Blackwell Superchip. Unlike a typical multi-GPU server, it has one GPU with 128GB of memory shared between the CPU and GPU. That means everyone using this machine is sharing the same GPU at the same time — there is no way to give each student their own card. Please read the Sharing the GPU section carefully.

Access is limited to students doing independent study in the department. Accounts are created manually by the instructor — you will be told your username in advance.

02 Connecting to the Machine

Two paths depending on whether you're on campus network or not.

On campus network

If you're on Montclair State's campus network (e.g. campus WiFi), you can SSH directly:

ssh your-username@spark.cs.montclair.edu

Off campus

If you're off campus, you need to first get onto the campus network through the university's VDI portal, then SSH from there.

  1. Go to vdi.montclair.edu
  2. Log in with your NetID and complete Duo two-factor authentication
  3. Launch the assigned virtual desktop
  4. Open a terminal inside the virtual desktop and SSH from there: 
    ssh your-username@spark.cs.montclair.edu
Note: Replace your-username with the username you were given.

03 First Login Checklist

A few things to do the first time you log in.

  1. Change your password to something only you know: 
    passwd
  2. Check the GPU is healthy and see who else might be using it: 
    sparktop
    This machine has a single GPU with unified memory shared between CPU and GPU, so the usual nvidia-smi command can't report memory usage correctly here (it will show "Not Supported"). sparktop is a tool written for this box specifically — it shows GPU utilization, unified memory usage, and exactly who is running what. You'll actually see a short version of this automatically every time you SSH in. Use sparktop -w to watch it live (refreshes every 2 seconds, Ctrl-C to quit).

    Here's what it looks like when someone is actually training a model — GPU-MEM and SM% are non-zero, and there's a real process attached:

    GPU0 NVIDIA GB10   |||||||||||||||||||.  96.0%  sm 2509/3003MHz  pwr 82W  temp 49C  no throttling
MEM |................... 5.5G/121.7G used   free 116.2G   gpu-held 1.3G

USER            PID   GPU-MEM   SM%   CPU%     RSS     TIME T COMMAND
alice         84183      1.3G    84     99  126.3M     0:03 C python3 train.py

    Here, alice is holding 1.3G of GPU memory and using 84% of the GPU's compute. Don't start a heavy job of your own right now — wait or ask her when she'll be done.

  3. Check your architecture (this machine is ARM64, not the usual x86_64 — matters for the next step): 
    uname -m
# should print: aarch64

04 Setting Up Your Python Environment

Everyone installs their own Miniconda in their own home directory — environments are not shared.

Important: This machine uses an ARM64 (aarch64) CPU, not the standard x86_64 used on most laptops/servers. You must download the aarch64 build of Miniconda, or the installer will fail or run under emulation.

1. Download and install Miniconda

cd ~
wget https://repo.anaconda.com/miniconda/Miniconda3-latest-Linux-aarch64.sh
bash Miniconda3-latest-Linux-aarch64.sh

Accept the license, keep the default install location, and say yes when asked whether to run conda init.

2. Reload your shell

source ~/.bashrc

3. Create your own environment

conda create -n myenv python=3.11
conda activate myenv

Install whatever packages your project needs (e.g. pip install torch) inside this environment. Since the GPU is shared, only install/run what you actually need — see the next section.

06 Sharing the GPU read this

There is one GPU for everyone. These rules exist to keep it usable for all of you.

  • Always run sparktop before starting a job. If GPU memory or utilization is already high, someone else is using it — wait or coordinate with them before launching your own job. (Don't rely on plain nvidia-smi here — on this unified-memory GPU it can't report memory usage correctly.)
  • Don't leave idle notebooks or sessions holding GPU memory. A Jupyter kernel or Python shell that's just sitting there importing torch can still reserve GPU memory nobody else can use. Shut down what you're not actively using.
  • Use tmux or screen for long-running jobs so you can disconnect without killing your process — but remember to close the session and free the GPU once the job finishes. Don't use it as an excuse to hold the GPU indefinitely.
  • Coordinate with the other students if you know you need a long block of GPU time (e.g. a multi-hour training run). A quick message to the group avoids collisions.
  • Clean up when you're done — exit your script normally, shut down the Jupyter kernel from the notebook interface, and close your tmux/screen session once the job finishes, instead of just disconnecting and leaving it running.

There's currently no automated queueing system (like Slurm) on this machine — sharing works on courtesy and communication. That may change later if conflicts become frequent.

07 Troubleshooting

Common issues and what to check first.

ProblemTry this first
SSH connection times out / refused Confirm you're on campus network or connected through vdi.montclair.edu first. Double-check the hostname and your username.
CUDA out of memory Run sparktop — someone else is likely using GPU memory. Wait, or ask in the group chat.
Miniconda installer fails or runs strangely slow Make sure you downloaded the aarch64 installer, not x86_64.
Forgot password / locked out Email Junyi Ye — passwords can't be self-reset.
Need a package/tool that requires sudo Don't try to work around it — email Junyi Ye and ask.
